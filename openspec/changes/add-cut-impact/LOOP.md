## Facts that are easy to get wrong

- **The tree.** Each NAP has one `parent` (the OLT or a NAP) and exactly one incoming run whose
  `to` is that NAP. There are two cascades: NAP-03 → NAP-12 (over FR-12), and NAP-04 → NAP-09 (over
  FR-09). Subscribers per NAP:
  - NAP-01: SUB-001–003; NAP-02: 004–005; NAP-03: 006; NAP-04: 007–008; NAP-05: 009–010;
  - NAP-06: 011–013; NAP-07: 014–015; NAP-08: 016–017; NAP-09: 018–020; NAP-10: 021–022;
  - NAP-11: 023–024; NAP-12: 025–028.
- **Cut semantics** (spec `cut-impact`):
  - A run cut puts its `to` NAP and everything below it out of service.
  - A NAP cut puts that NAP (listed among `naps_out_of_service` too) and everything below it out of
    service, and its feeder run stays lit.
  - `runs_out_of_service` holds downstream runs only (`from` is an out-of-service NAP), never the
    cut run itself.
  - Every list is sorted by id. `counts` holds the list lengths.
- **Refusals:** the OLT id throws exactly `A cut at the OLT is not supported`, and an unknown id
  throws a message naming it.
- **The payload** keeps every existing variant unchanged and adds impact variants with
  `status: "cut" | "out_of_service"` and **no `margin_db`**. A subscriber impact entry still
  carries `nap_id`.
  - Severity: pass 0 < marginal 1 < fail 2 < out_of_service 3 < cut 4. A merge into a more severe
    impact status replaces the entry whole, so no margin survives.
  - `fit_bounds` is true when any NAP, subscriber or cut-run entry exists.
- **`highlightIds`** returns NAP ids, subscriber ids, and the ids of run entries **whose status is
  `cut`**, and nothing else. The abstention grader uses it too.
- **Oracle ids** in eval cases may now be fiber runs too: extend the validator.
- **The oracle** `seed/expected-cut-impacts.json` is written **by hand** (design.md, decision 8),
  not generated by a script. Check it against design.md's Context table and the facts above. A
  separate test asserts the handoff's values directly: FR-03 → 5, FR-12 → 4, FR-04 → 5.
- **Map:** MapLibre cannot drive `line-dasharray` from feature-state. Make the cut and dark styles
  differ by colour, width and opacity (design.md, decision 6). Runs use the `onPath` feature-state
  key, NAPs and subscribers use `status`.
- **The prompt hash** before this change is `c20ecc7407bf`. It must change in 3.3, which is
  expected.
- **Tooling quirk:** on this Windows setup, Bash heredocs containing apostrophes have failed to
  parse. Use the Edit and Write tools for source edits.
- Vitest runs in `node` and only picks up `src/**/*.test.ts`. Do not add jsdom or component tests.

## The loop

Repeat until every task in groups 1–4 is done:

1. Take the **first** unchecked task in groups 1–4 of `tasks.md`.
2. Implement exactly that task, with every test it lists.
3. Run `npm test`, `npm run lint` (no warnings) and `npx tsc --noEmit`. Fix until all three pass.
4. Do the task's own "Verify" steps. For 2.3, do everything except the browser check.
5. Tick it (not 2.3), and commit the code and `tasks.md` together, with a message like
   `Add the cut traversal (add-cut-impact 1.2)` ending with the line
   `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
6. Next task.

**Stop and report instead of guessing** when:
- the same task fails its checks three attempts in a row;
- the engine and the hand-written oracle disagree (do not edit either to match);
- a task seems to need something the hard rules forbid;
- the spec and the code disagree in a way the facts above do not settle.

Leave that task unchecked and describe the blocker.

## Final report

When done or stopped, report:

- the final test count;
- the new prompt hash (12 characters);
- the compare output of the 2.4 re-grade check;
- anything you found ambiguous, and how you resolved it.
