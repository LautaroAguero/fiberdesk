# Grounding grader — hand validation

The grounding grader is only trusted once a person has checked its verdicts against real answers,
number by number (`openspec/changes/archive/2026-10-08-add-eval-harness/design.md`, decision 8; tasks 10.3).

## Round 1 — `evals/runs/2026-10-08T03-32-06Z.json`

First baseline run: `claude-opus-5`, effort `low`, prompt `fa57f136375a`. All **21** final answers
were read — every area, every answer the grader flagged — and every figure in each was checked
against the tool results the model saw (rebuilt by re-dispatching the recorded calls).

### Flagged figures

| Case | Figure | Grader | Human | Why |
|---|---|---|---|---|
| `budget-failing-en` | 3.00 | ungrounded | **grounded** | "below the 3.00 dB recommended minimum" after a survey-only turn. The survey's rows carry no threshold; 3.00 is stated in the survey tool's own definition, which code wrote. **False positive.** |
| `budget-limit-es` | 3,00 | ungrounded | **grounded** | Same cause: "con el umbral estándar de 3,00 dB" after a survey-only turn. **False positive.** |
| `budget-why-nap12-es` | 20 | ungrounded | ungrounded | "casi 20 km de fibra acumulada" — 11.2 + 8.6 = 19.8, summed and rounded by the model. True positive. |
| `conv-and-nap12-es` | 0.23 | ungrounded | ungrounded | "con 0.23 dB de recuperación bastaría" — 3.00 − 2.77, subtracted by the model. Correct arithmetic, but the project's rule is that the model does none. True positive. |
| `conv-second-one-en` | 19.8 | ungrounded | ungrounded | "~19.8 km of total fiber" — 11.2 + 8.6, summed by the model. True positive. |

### Figures the grader passed

Every other figure in the 21 answers was checked and is a value the tools returned: totals,
margins, received power (e.g. −12.68 dBm for NAP-07 is its `rx_power_dbm`, not a subtraction the
model did), per-hop fiber, splitter, connector and splice figures and their counts, by-source
totals, class budgets and constants. No figure the model invented or re-derived was passed.
**False negatives: 0.**

Two blind spots were seen but did not hide an error this time, and stay documented limits rather
than fixes:

- **Counts written as words** are not figures to the grader: "Las nueve restantes pasan", "Dos
  cajas", "One NAP fails". All were correct here, but a wrong count in words would pass.
- **Membership, not attribution**: small integers such as connector counts (3) and splice counts
  (6, 5) were all attached to the right run here; the grader would not notice if they were not.

### Result and fix

- True positives: 3. False positives: 2 (one cause). False negatives: 0.
- **Fix:** the tool definitions the model was given are now a grounding source, alongside tool
  results and the user's messages — they are generated by code, and the survey's default threshold
  is stated only there. A test pins that the definitions contribute exactly one figure (3), so any
  new number added to a tool description has to be a deliberate choice. Regression test: the
  verbatim `budget-failing-en` sentence in `src/lib/evals/graders/grounding.test.ts`.
- Spec and design updated first (`assistant-evals`, "The grounding grader checks every number…";
  design decision 8).

## Round 2 — the same record, re-graded offline

`npm run eval:regrade -- evals/runs/2026-10-08T03-32-06Z.json` →
`evals/runs/2026-10-08T03-32-06Z.regraded.json`. No model call; the prompt hash matched, so the
tool definitions used are the ones the model saw.

- Both 3.00 / 3,00 flags are gone; the three true positives remain.
- No case changed outcome: both cases with a false positive also fail on their trajectory or
  highlight, independently of grounding.
- **False positives: 0.** The grounding grader can now gate a decision.

## Product findings (not grader errors)

Recorded here because the validation surfaced them; they are behaviours, and the eval reports them
as failures on purpose.

- **Re-derived figures** in three answers (20, 19.8, 0.23) — the core rule broken in prose that
  is otherwise correct.
- **`budget-rx-nap09-es`**: asked for the power reaching NAP-09, the model answered from the survey
  alone and stated that "the system does not model received optical power in dBm". It does —
  `detail_optical_budget` returns `rx_power_dbm` (−26.4 dBm for NAP-09). A wrong decline, which
  the trajectory and figures graders catch.
- **`budget-failing-en`**: the reference question in English was answered from the survey and the
  detail was offered rather than fetched, so the map highlighted nothing. The Spanish phrasing
  surveyed and then detailed both NAPs. The Phase 1 hand verification shows the same English
  behaviour.

## Case correction — `budget-limit-es` (owner decision, 2026-10-08)

Not a grader error but a case error, found while reading the same run. `budget-limit-es` ("¿hay
alguna caja al límite del margen?") required the highlight to contain NAP-12, which contradicts
design decision 7 — highlight is graded only where the reference behaviour needs a detail call,
and the survey alone answers this question. Its recorded answer named NAP-12 (2.77 dB, marginal),
NAP-06 and NAP-09, every figure grounded; it failed only on the highlight.

The expectation was removed and the record re-graded offline (no model call). It moves the case
from fail to pass and the overall rate from 15/21 to 16/21. Because it raised the pass rate after
seeing results, the owner made the call explicitly, and it is recorded here and in design.md
(decision 14) rather than made silently. No other case was touched.
